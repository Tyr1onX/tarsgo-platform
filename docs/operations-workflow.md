# 公共运营事务协作板：产品工作流

## 产品定位

TARS-Go 当前阶段服务高校机器人团队的公共运营事务协作，而不是替代聊天工具，也不是技术研发项目管理系统。

讨论仍发生在微信、会议或线下沟通中。TARS-Go 只记录已经明确下来的工作，并持续反映当前真实状态：做什么、谁负责、谁协作、什么时候完成、当前进行到哪里。

当前优先覆盖运营、宣传、活动执行、纳新、物资、直播、摄影等公共事务。机械、电控、算法等技术研发流程不在本阶段范围内。

## 事项与分工

一个根任务代表一件事项，例如“春屿展示”。事项可以在执行过程中逐步增加一级分工，例如：

- 准备机器人
- 周边物资保障
- 现场摄影
- 直播间值守

创建事项时不要求一次把全部分工想清楚。工作本身允许持续修改；随着信息明确，管理者可以继续补充、调整或重新分配分工。

当前只支持一级分工，不建立无限层级。

## 任务颗粒度

是否应该拆分一项工作，主要看以下因素：

1. 时间：是否发生在不同时间段，或需要分别等待。
2. 地点：是否在不同地点执行。
3. 人员连续性：是否适合同一个人连续完成。
4. 交接点：中间是否存在明确的交接、确认或移交。
5. 完成标准：是否具有不同的可独立验收结果。

同一个责任链上、适合连续完成的动作可以合并。例如拿取周边、带到现场并负责发放，如果时间地点连续且没有明确交接点，可以作为一个分工。

同时发生且无法由一个人兼任的工作应拆开。例如直播值守和现场摄影需要同时执行时，应形成两个独立分工。

## 分配方式

正式运营任务同时支持两种负责人形成方式：

- 管理者直接指定负责人。
- 暂不指定负责人，开放给 active 成员主动认领。

任务还可以：

- 预先指定协作者。
- 开放协作，让 active 成员自行加入或退出。

正式发布的任务必须满足至少一个条件：

- 已指定负责人；或
- 开放负责人认领。

不允许存在既没有负责人、又不能被认领的正式任务。

## 全员可见

所有正式发布的运营事项和分工对 active 成员可见。

成员在任务页使用三个核心视角：

- **我的**：自己负责或参与协作的工作。
- **待认领**：还没有负责人且开放负责人认领的工作。
- **全部**：全队已经正式发布的运营事项和分工。

“全部可见”不等于“全部可编辑”。结构性修改仍由 admin / manager 完成。

## 执行状态

任务继续使用三个状态：

- todo
- doing
- done

负责人可以更新自己负责任务的执行状态。admin / manager 可以持续修改标题、负责人、协作者、截止时间、完成标准和开放状态。

发布不是冻结点。真实工作发生变化时，系统应允许把确定后的新状态更新进去。

本阶段不实现完整变更历史，但后续需要为负责人、时间、完成标准、开放状态等关键字段记录重要变更，便于复盘和追踪交接。

## 当前数据表达

V0.2 第一阶段继续演化现有 Task：

- 根任务：事项。
- parent_id 指向根任务：一级分工。
- owner_id：负责人，可为空。
- owner_claimable：负责人为空时是否允许公开认领；已认领后保留该属性，用于安全取消认领并重新开放。
- collaborators：指定协作者。
- collaboration_open：是否允许成员自主加入 / 退出协作。
- deliverable：完成标准，可为空。
- execution_points：最多 6 条简短执行要点。
- cautions：最多 5 条与任务相关的注意事项。
- prerequisites：最多 4 条前置条件说明；仅供阅读，不形成系统依赖或阻塞。
- deadline：每个事项和分工都保存自己的明确截止时间。

子任务创建时，前端可以预填父事项截止时间，但数据库不做隐式继承。

## 动态事项执行

现实中的事项会随着沟通和执行持续变化。当前仍以根 Task 表示事项，不新增 Item 聚合模型。

- root Task 的 `context_facts` 保存当前已经确认、后续执行可以直接依赖的事实。
- 每个 Task 的 `result` 保存实际执行后得到的结果，与“做到什么算完成”的 `deliverable` 分开。
- `ItemActivity` 只记录事项过程中人工确认的动态，始终挂在 root Task 上。
- 事项参与者可以记录动态，并选择把同一段内容同时加入当前事实；两步在一个事务中完成。
- 任务结果只有经过人工确认后才能加入事项当前事实，同时生成一条事项动态。
- 删除过期或错误的当前事实不会删除历史动态。

事项参与者当前定义为 admin / manager、事项负责人、任意一级分工负责人或一级分工协作者。其他 active 成员可以读取，但不能修改事项当前事实或动态。

本阶段先把现实变化可靠记录下来，不因记录动态而自动调用 AI、修改任务、调整截止时间或重新规划。后续 AI 检查方案时再把事项描述、当前事实、任务状态与结果、最近动态和 Knowledge 作为输入。

## 当前阶段明确不做

V0.2 第一阶段不实现：

- AI API 或 LLM provider
- 自动排班
- 时间冲突计算
- 工作量算法
- 任务推荐算法
- 通知
- 评论
- 文件
- 请假
- 周报
- 技术研发管理
- 复杂看板
- 复杂组织架构

这些能力只有在真实工作流需要时再逐步加入。
